1 · Frontend Performance

Data Fetching

Critical Sequential waterfall fetches on Guest Management page app/admin/guests/page.tsx — fetchGuestData() lines 203-262

Three API calls (guests, RSVPs, plus-ones) run sequentially. Each waits for the previous to finish, adding 300-500 ms of unnecessary latency on every load and every 30-second poll cycle.

// Current — sequential
const guestsResponse = await fetch(`/admin/guests?wedding_id=...`);
setGuests(normalizedGuests);
const rsvpsResponse = await fetch(`/admin/rsvps?wedding_id=...`);   // waits
const plusOnesResponse = await fetch(`/admin/plus-one/wedding/...`); // waits again
Fix: Wrap all three in Promise.all() — same pattern the Budget page already uses successfully (budget/page.tsx line 217).
High Full data refetch after every CRUD operation app/admin/guests/page.tsx — lines 587, 665, 683

After adding, editing, or deleting a single guest, fetchGuestData() re-downloads the entire guest list, all RSVPs, and all plus-ones. For a 500-guest wedding this is ~3 full HTTP round-trips to change one record.

Fix: Optimistically update local state for add/edit/delete, then confirm with a lightweight HEAD or single-record GET.
Medium 30-second polling fetches everything regardless of changes app/hooks/usePolling.ts — guests & planner pages

The polling hook refetches all data unconditionally every 30 seconds. There is no ETag, If-Modified-Since, or server-side change-detection to skip unnecessary transfers. For large datasets this is wasteful.

Fix (short-term): Add an ETag or last_modified header to list endpoints; skip the full fetch when data is unchanged. Fix (long-term): Replace polling with Server-Sent Events (SSE) from FastAPI.

Re-renders & Component Architecture

Critical Monolithic pages with 25-30 useState declarations app/admin/guests/page.tsx (30+ states) · reminders/page.tsx (25+) · budget/page.tsx (25+)

Every state change (typing in search, toggling a filter, opening a modal) triggers a full re-render of the entire page — including the guest table, toolbar, modals, and action buttons. React 19 batches state updates within a single event, but cross-event updates still cascade.

Fix: Extract sub-components (GuestTable, GuestToolbar, GuestModals) with their own local state. Use React.memo() on the table rows. Move filter/search state into a dedicated useReducer().
High Inline component definitions recreated every render app/admin/guests/page.tsx — NotificationIcons (line 392), SortIcon (line 540)

Helper components like NotificationIcons and SortIcon are defined inside the parent component body, so React treats them as new component types on every render — destroying and recreating their DOM.

Fix: Move these to module-level const declarations outside the parent component.
Medium O(n) plus-one lookup on every guest row render app/admin/guests/page.tsx — getPlusOnesForGuest (line 368)

plusOnes.filter(p => normalizeId(p.guest_id) === guestId) runs a full array scan for each guest rendered. With 500 guests and 100 plus-ones, that is 50,000 comparisons per render.

Fix: Build a Map<string, PlusOne[]> indexed by guest_id once after fetch (via useMemo), then do O(1) lookups.

Bundle & Code Splitting

High Three.js (~600 KB) loaded on landing page without dynamic import package.json — @react-three/fiber, @react-three/drei, three

The 3D canvas and supporting libraries are statically imported. Every visitor downloads ~600 KB of JavaScript even if their device prefers reduced motion or the hero canvas is off-screen.

Fix: Use next/dynamic(() => import('./HeroCanvas'), { ssr: false }) and gate on prefers-reduced-motion.
Medium No list virtualization for large datasets app/admin/guests/page.tsx · budget/page.tsx

Guest tables and budget category lists render every row into the DOM. Performance degrades noticeably past ~200 items with full re-renders.

Fix: Add react-window or @tanstack/react-virtual for any list exceeding 50 rows.
Low Feature carousel animates off-screen app/page.tsx — FeatureShowcase (line 248)

The 4-second setInterval runs continuously. When the section scrolls out of view, it still triggers state updates and image transitions.

Fix: Pause the interval when an IntersectionObserver reports the section is not visible.

2 · Backend Performance

N+1 & Loop-Based DB Writes

Critical Per-guest update_one() inside email send loop app/services/email_service_resend.py — send_rsvp_invitations() line 240

After each successful email send, the code calls await self.guest_collection.update_one() individually. Sending invites to 500 guests means 500 separate MongoDB write operations.

async for guest in guests:
    result = await self.send_email(...)
    if result["success"]:
        if not guest.get("invite_sent"):
            await self.guest_collection.update_one(   # N+1 write
                {"_id": guest["_id"]},
                {"$set": {"invite_sent": True, ...}}
            )
Fix: Collect successfully-sent guest IDs in a list, then do one update_many({"_id": {"$in": sent_ids}}, {"$set": {...}}) at the end.
Critical Same N+1 pattern in SMS send loop app/services/reminder_utilities.py — send_personalized_rsvp_links() line 58

Identical issue: each successful SMS triggers an individual update_one(). Additionally, the Twilio messages.create() call is synchronous (blocking) inside an async function.

Fix: Batch DB writes with update_many(). Wrap Twilio calls with asyncio.to_thread() or use TwilioHttpClient(timeout=5).
High Triple DB round-trip for single guest update app/api/guest.py — update_guest() lines 101-138

Updating one guest field triggers: (1) find_one() to verify access, (2) update_one() to apply changes, (3) find_one() again to return the updated document.

Fix: Use find_one_and_update(return_document=ReturnDocument.AFTER) to combine steps 2 and 3 into one call.

Unbounded Queries

High .to_list(length=None) without pagination on list endpoints app/services/guest_service.py · wedding_service.py · guest_export_service.py

Multiple services call .to_list(length=None) to load entire collections into memory. A wedding with 5,000+ guests would transfer and serialize all records in a single response with no pagination.

Fix: Add skip / limit query params to list endpoints. Default to 100 items. For exports, stream with a cursor instead of to_list().
Medium Wedding list returns full documents without projection app/services/wedding_service.py — list_weddings() line 108

await self.collection.find().to_list(length=None) returns every field of every wedding (including nested events, FAQs, registries) when the frontend only needs id, slug, couple_names, and date for the selector dropdown.

Fix: Add a projection: .find({}, {"_id": 1, "slug": 1, "couple_names": 1, "date": 1}).

External API Calls — Missing Safeguards

Critical No timeout on Twilio, Resend, or Stripe API calls reminder_utilities.py:53 · email_service_resend.py:97 · stripe_service.py:85

All three external services are called without timeout configuration. A single hung connection to Twilio during a bulk SMS send will block the entire request indefinitely, eventually timing out at the HTTP gateway level (30-60 s) with no user feedback.

Fix: Set TwilioHttpClient(timeout=5), wrap Resend calls in asyncio.timeout(10), set stripe.api_request_timeout = 10.
High Synchronous Twilio call in async event loop app/services/reminder_utilities.py — line 53 · reminder_service_twilio.py — line 79

self.twilio_client.messages.create() is a blocking HTTP call running on the async event loop. During a 500-guest SMS send, the event loop is blocked for each call (~200-500 ms each), preventing other requests from being served.

Fix: Wrap in await asyncio.to_thread(self.twilio_client.messages.create, ...) or use a ThreadPoolExecutor with concurrency limit.

Auth & Middleware Overhead

Medium Redundant user DB lookups on every authenticated request app/dependencies/auth_extended.py — get_current_user_extended() lines 113, 129

Each API request decodes the JWT, then does 1-2 find_one() calls to look up the user profile. For the 30-second polling cycle across 3 admin pages, that is ~6 DB reads per minute per active planner just for auth.

Fix: Cache user profiles in a TTL dict (5-minute expiry) keyed by email. The JWT already contains the email — only re-fetch from DB on cache miss.
Low Synchronous file-based audit logging in middleware app/middleware/audit_logging.py — dispatch() line 182

The audit middleware writes to a log file synchronously after every response, adding 1-5 ms of blocking I/O.

Fix: Switch to asyncio.create_task() for file logging, same as the DB logging path already does.

3 · API Alignment

What's Working Well

Aligned Core CRUD endpoints are correctly wired

Guest CRUD, wedding CRUD, budget operations, seating/table management, QR export, and plus-one endpoints all have matching frontend calls and backend routes. The middleware matcher correctly excludes static files and API routes.

Aligned Reminder endpoints correctly distributed across API files

/admin/reminders/send (reminder.py), /admin/reminders/send-to-guests (reminder_twilio.py), /admin/reminders/send-personalized-links (reminder_utilities.py), and /admin/email/send-reminder-individual (email_reminders.py) all have matching backend handlers.

Issues Found

High No 401 handling — expired sessions silently fail app/admin/hooks/useTables.ts · app/admin/hooks/useGuests.ts · app/admin/guests/page.tsx

Most fetch calls catch errors generically but don't distinguish between 401 (token expired) and 500 (server error). When a planner's JWT expires mid-session, API calls fail silently — the UI shows "Failed to load" instead of redirecting to login.

// Current — generic error
} catch {
  setError('Failed to load guest data');
}

// Should detect 401 and redirect
if (response.status === 401) {
  logout();           // clear token
  router.push('/admin/login');
  return;
}
Fix: Add a shared handleApiResponse() utility or Axios interceptor that catches 401 globally and triggers logout().
Medium Budget API response shape inconsistencies app/services/budgetApi.ts — lines 49-50, 113-114

The frontend budget service sometimes expects {message, category} and other times handles a raw array. The defensive parsing (Array.isArray(data) ? data : data.quotes || []) works but indicates the API contract isn't formalized.

Fix: Standardize all list responses as {items: [...], total: N}. Standardize mutations as {success: true, data: {...}}.
Low Deprecated SMS callback endpoints still active app/api/reminder.py — lines 27-57

GET/POST /admin/reminders/sms-callback is marked DEPRECATED with a suggestion to use /webhook/twilio/incoming, but the routes are still registered and reachable.

Fix: Return 301 redirect to the new endpoint, or remove after verifying Twilio webhook config is updated.

Overall Verdict

The architecture is sound and the API surface is well-aligned — no missing or broken endpoints were found. The main performance bottlenecks are: (1) sequential fetch waterfalls on the frontend, (2) per-record DB writes in bulk operations, and (3) blocking external API calls without timeouts. Fixing items 1-3 in the action plan above would immediately improve perceived latency by 40-60% for the most common planner workflows. The database indexes are comprehensive and well-designed.
