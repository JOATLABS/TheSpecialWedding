Critical Issues — Fix Before Deploy

CRIT-1: Unsubscribe tokens have no expiration

File: planner_onboarding_email_service.py line 559

Unsubscribe tokens are generated with secrets.token_urlsafe(24) (which is cryptographically secure), but stored permanently with no TTL. A leaked token grants permanent unsubscribe access. Add an unsubscribe_token_created_at field and validate tokens are no older than 90 days.

CRIT-2: No rate limiting on public unsubscribe endpoints

File: app/api/user_management.py lines 379-396

The GET /planner-onboarding/unsubscribe/status and POST /planner-onboarding/unsubscribe endpoints are public with zero rate limiting. Combined with no token expiration, this creates a brute-force vector. Implement rate limiting (5 requests/minute per IP) using slowapi or middleware.

CRIT-3: Email template variables not HTML-escaped

File: planner_onboarding_email_service.py lines 752, 768

User-controlled fields (company_name, role) are inserted into HTML email bodies via f-strings without escaping. A user with company_name = '<img src=x onerror="alert(1)">' gets their XSS rendered in every onboarding email. Fix with from html import escape on all user-sourced values.

# Current (unsafe):
f'at <strong>{user.get("company_name")}</strong>'

# Fixed:
from html import escape
f'at <strong>{escape(user.get("company_name", ""))}</strong>'

Cross-Team Consistency Issues

HIGH: features/page.tsx comparison table ignores Team 6's downgrade recommendations

This is the most significant cross-team inconsistency.

Team 6's research flagged several comparison rows as "Adjacent" (not binary true/false), including:

  • SMS & Email Reminders with Fallback — all competitors marked "Adjacent", not flat "No"
  • Couple Portal — research calls this "the biggest terminology mismatch" with HoneyBook's Client Portal
  • AI Contract Generation — all competitors marked "Adjacent"
  • Custom Forms Builder — all competitors marked "Adjacent"

The /compare pages (Team 4) do properly use confidence levels with the evidence layer. But the /features comparison table (Team 2) still presents binary checkmarks/dashes without qualification. This creates a legal inconsistency — two pages on the same site make different claims about the same competitors.

Fix: Either add confidence qualifiers to the features table, add a disclaimer linking to the /compare pages for detailed evidence, or use a three-state system (checkmark / partial / dash) instead of binary.

MEDIUM: CHANGELOG claims confidence labels were "inlined" but they're only on /compare, not /features

CHANGELOG entry states "Inlined the public source ledger, row-level confidence labels, and official evidence URLs" — this is true for /compare/[competitor] pages but NOT for the main /features comparison table, which is the more prominent surface.

MEDIUM: Audit date synchronization across teams

The audit date "April 6, 2026" appears in: Team 4's data.ts, page.tsx, [competitor]/page.tsx, evidence.ts + Team 6's research doc + Team 2's features page (implicitly). No single source of truth — quarterly updates will be error-prone. Extract to one shared constant.
