Critical Findings (Fix Before Deploy)

1. No Rate Limiting on Unsubscribe Endpoints CRITICAL Security

File: app/api/user_management.py lines 379-396

Both the GET status check and POST unsubscribe confirmation endpoints are tagged as "Public" but have zero rate limiting. An attacker can enumerate unsubscribe tokens by rapidly querying /planner-onboarding/unsubscribe/status?token=X, then unsubscribe planners without consent.

Fix: Add rate limiting: 5-10 requests/minute per IP on these endpoints via your rate_limiting.py middleware configuration.

2. Missing CSRF Exclusion for Unsubscribe POST CRITICAL Security

File: csrf_protection.py lines 32-48

The POST /planner-onboarding/unsubscribe endpoint uses token-based auth (no session cookie), similar to password reset. However, it's not in the CSRF exclusion list. POST requests may fail CSRF validation in production, or if the middleware is permissive, it's an unintentional security gap.

Fix: Add /planner-onboarding/unsubscribe to exclude_paths in csrf_protection.py (since it uses token-based auth, not sessions).

3. Published Comparison Table Contradicts Research Doc CRITICAL Legal

Files: app/features/page.tsx lines 23-41 vs docs/research/competitor-comparison-april-2026.md lines 74-86

The research doc carefully classifies competitor capabilities as "Confirmed", "Adjacent", or "Not found". However, the public comparison table on /features uses hard binary checkmarks (✓/✗) with none of these qualifications applied. Specific problematic rows:

  • Client Portal: Shows competitors as ✗ but research says "Adjacent" (client portals exist for all three)
  • SMS & Email Reminders: Shows HoneyBook/Aisle as ✗ but research says "Adjacent"
  • AI Contract & E-Sign: Shows all as ✗ but competitors have non-AI contracts/e-sign ("Adjacent")
  • Budget Management: Shows all as ✓ but research says HoneyBook/Planning Pod are only "Adjacent"

Fix: Either add "Adjacent" badges for gray-area features, or use partial-check (•) icons with a footnote explaining the distinction. Also add "Last verified: April 6, 2026" to the table header.

Team 3: Dynamic OG Images

B
Solid implementation, needs hardening. Edge runtime OG generation works well; missing input validation and timeouts.

Files touched: app/api/og/route.tsx, app/lib/og-utils.ts

What went right: Clean ImageResponse API usage. Blog and vendor variants render correctly. Fallback cards for missing data. Caching headers present.

Issues found:

  • No input validation on slug/id params (Medium): .trim() only — no format check. Add regex validation.
  • No fetch timeout (Medium): Edge function can hang indefinitely on slow API. Add AbortSignal.timeout(5000).
  • Silent error handling (Low): Catch returns fallback without logging. Add structured error logging.
  • Unvalidated API response shapes (Medium): Use Zod for runtime validation of blog/vendor JSON.
  • Brand colors hardcoded in route (Low): Should import from design tokens or constants.

Team 4: Comparison Hub

B+
Well-architected evidence layer. Clean data/evidence separation, but needs type safety and decomposition.

Files touched: app/compare/layout.tsx, app/compare/page.tsx, app/compare/data.ts, app/compare/[competitor]/page.tsx, app/compare/evidence.ts

What went right: Evidence layer with per-row confidence levels and clickable source URLs. JSON-LD structured data (BreadcrumbList, FAQPage, WebPage). Graceful handling of unknown competitor slugs. Audit qualifier ("as of April 2026") on every page.

Issues found:

  • Evidence rows not validated against comparison rows (High): Silent "N/A" when evidence is missing. Add build-time assertion.
  • Confidence semantics undocumented (Medium): "High" on "not found" rows is ambiguous. Add enum with descriptive comments.

  • Hardcoded base URL (Medium): Should use process.env.NEXT_PUBLIC_APP_URL.
  • Source code references are brittle strings (Medium): "HB1-HB7" could drift. Use typed const assertions.

Team 5: Email Sequence + Unsubscribe

C+
Strong backend logic, weak security posture. Claim-based locking and sequence state machine are excellent, but public endpoints are under-protected.

Files touched: app/services/planner_onboarding_email_service.py, app/services/user_management_service.py, app/api/scheduler_jobs.py, app/api/user_management.py, app/unsubscribe/planner-onboarding/page.tsx, tests/backend/test_planner_onboarding_email_service.py, .gitignore

What went right: 6-email sequence matches audit spec exactly (Day 0/1/3/5/8/12). Conditional skip logic for wedding-created and team-exists. Exit paths for Signature upgrade and 14-day inactivity. Claim-based locking prevents concurrent sends. Token uses secrets.token_urlsafe(24) (192 bits). Test coverage for main paths.

Issues found:

  • No rate limiting on public endpoints (Critical): Enables token enumeration attack.
  • Missing CSRF exclusion (Critical): POST unsubscribe may fail CSRF checks or create unintentional gap.
  • Token exposed in URL via GET param (High): Visible in browser history and referrer headers. Consider POST-only flow.
  • Tokens not invalidated after use (Low): Replay is possible (idempotent, but bad practice).
  • Missing test: token enumeration resistance (Medium): No test verifying rate limiting behavior.
  • Missing test: one-time use (Medium): No test verifying token invalidation after unsubscribe.
  • No error handling on sequence start (Medium): user_management_service.py:1018-1022 — if start_sequence() fails, onboarding silently never starts.
  • Email templates are inline HTML strings (Medium): 45+ lines of HTML per template. Extract to template files.
