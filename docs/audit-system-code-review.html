1. Review Dimensions

Security FAIR

Auth flows have constant-time password comparison and timing-attack resistance. However, several services perform hard deletes without pre-delete audit snapshots. Cascade delete touches 20+ collections with no immutable record of what was destroyed. The guest_export_service has unescaped HTML rendering of guest PII in PDF generation.

Performance GOOD

Existing audit middleware uses async background tasks for DB writes — smart design. The new compliance layer can follow the same fire-and-forget pattern. Middleware stack order is correct. No N+1 queries detected in audit paths. Team data cache with TTL and bounded eviction is well-designed.

Correctness FAIR

Stripe webhook handling has proper idempotency with status lifecycle tracking. But cancel_subscription does best-effort Stripe cancel then continues locally regardless — possible split-brain. Several services silently swallow audit logging failures, which is appropriate for non-blocking but means compliance events can be silently lost.

Maintainability NEEDS WORK

Four separate audit systems exist (audit_logs, security_audit_logs, activity_logs, admin_activity_log) with different schemas, retention periods, and query patterns. No unified event vocabulary. The compliance layer will be the fifth — critical to design it as the canonical source and bridge the others into it, not create yet another silo.

2. Critical Findings

C1: Cascade Delete Has No Pre-Delete Audit Snapshot

CRITICAL · GDPR + SOC 2

app/services/cascade_delete_service.py · soft_delete_wedding() / hard_delete_wedding()

hard_delete_wedding permanently removes records from 20+ collections including guests (PII), contracts (financial), and payment records. There is no snapshot of what was deleted written to an immutable store before the operation executes. The activity_log entry is written inside the same try/except that swallows errors — if it fails, the deletion proceeds silently.

Impact: Under GDPR, you must be able to demonstrate what data existed and why it was deleted. Under SOC 2, mass data destruction without audit evidence is a material finding.

Fix: The compliance emitter must capture a pre-delete manifest (collection, count, sample IDs) and write it to D1 before the delete begins. The delete should be gated on successful audit write.

C2: Stripe Webhook Events Not Audit-Logged for PCI Traceability

CRITICAL · PCI DSS

app/services/stripe_service.py · handle_webhook_event() (line 1370)

Stripe webhook events (payment_intent.succeeded, charge.refunded, invoice.paid, subscription changes) are processed and stored in stripe_webhook_events collection with idempotency tracking, but no audit event is emitted to a compliance-grade store. The webhook event collection itself has no tamper evidence and lives alongside app data.

Impact: PCI DSS 4.0 requires a traceable audit trail for all payment-related actions. An auditor cannot independently verify that payment events were processed correctly without a separate immutable log.

Fix: Each webhook handler should emit a compliance event with stripe_event_id, event type, affected user, and the before/after subscription/payment state.

C3: No Before/After Snapshots on Data Mutations

CRITICAL · GDPR

All services performing update operations

GDPR's right of access requires you to demonstrate what data changed and when. Currently, no service captures the prior state of a record before updating it. The contract_service.update_contract(), vendor_service.update_vendor_profile(), wedding_service.update_wedding(), user_management_service.update_user(), and budget_service.update_budget_category() all overwrite data without snapshotting the old state.

Fix: The compliance emitter should fetch the current document before the update, diff it against the new state, and store both in the audit event's before_snapshot and after_snapshot fields.

C4: Guest Hard Delete Cascades Without Audit Trail

CRITICAL · GDPR

app/services/guest_service.py · delete_guest()

Guest deletion cascades to RSVPs and plus-ones with hard deletes — no soft-delete path exists. Guest data includes phone numbers, emails, dietary restrictions (potentially health-related PII under GDPR Article 9 "special category" data). Once deleted, there is no record that the data ever existed, making it impossible to respond to a GDPR subject access request about historical data processing.

Fix: Before deleting, emit a compliance event containing the guest's PII fields (redacted in the audit record per data minimization) and the deletion reason. Consider converting to soft-delete to support GDPR right-to-erasure requests that require confirmation.

C5: MongoDB Audit TTLs Destroy Compliance Evidence

CRITICAL · PCI + SOC 2

app/core/database_indexes.py · lines 651, 695

Current TTL indexes auto-delete audit data: audit_logs at 30 days, security_audit_logs at 180 days, activity_logs at 90 days, admin_activity_log at 90 days. PCI DSS requires 12 months of audit history. SOC 2 requires 12 months of continuous monitoring evidence. These TTLs destroy evidence before any compliance window closes.

Fix: This is exactly why the D1 compliance layer exists — it provides the long-term retention that MongoDB TTLs don't. The existing TTLs are fine for operational use; the compliance layer runs in parallel with 2-year retention.

3. Warnings

W1: Four Fragmented Audit Systems

WARNING · MAINTAINABILITY

audit_logs (middleware) · security_audit_logs (SecurityAuditService) · activity_logs (ActivityLogService) · admin_activity_log (AdminActivityService)

Each system has its own schema, event vocabulary, and retention policy. An auditor asking "who accessed contract #X on Tuesday?" would need to query four collections with four different query shapes. The new compliance D1 layer must be the canonical audit source that all four bridge into — otherwise you'll have five silos.

W2: Subscription Cancellation Split-Brain Risk

WARNING · CORRECTNESS

app/services/subscription_service.py · cancel_subscription()

Stripe cancellation is done best-effort: if the Stripe API call fails, the local subscription status is still updated to "cancelled." This can leave the Stripe subscription active while the app thinks it's cancelled. The compliance audit should capture both the Stripe response and the local state change to make this diagnosable.

W3: Form Response IP Addresses Stored Indefinitely

WARNING · GDPR

app/services/form_service.py · submit_form_response()

IP addresses are stored in form response documents with no TTL or anonymization. Under GDPR, IP addresses are personal data. The archival cron Worker should hash IPs in D1 after 90 days, but this local MongoDB storage also needs a separate cleanup migration or anonymization pass.

W4: Guest Export CSV Has No Persistent Audit Record

WARNING · GDPR

app/services/guest_export_service.py · export_form_responses_csv()

Bulk export of guest PII (names, phones, emails, dietary info) to CSV is logged only to the app logger (ephemeral). Under GDPR, bulk data exports are a significant processing event that must be recorded in an audit trail. The middleware will catch the HTTP request, but won't know it was a PII bulk export — service-level enrichment is needed to tag the event correctly.

W5: Budget Category Delete Cascades Quotes and Payments

WARNING · FINANCIAL

app/services/budget_service.py · delete_budget_category()

Deleting a budget category cascades to delete associated quotes and payment records — financial data that should be preserved for audit. No soft-delete path exists. The compliance emitter should snapshot all affected financial records before deletion.

W6: Auth Service Doesn't Log Failed Login Details

WARNING · SOC 2

app/services/auth_service.py · authenticate_user() (line 20)

Login failures raise HTTPException but don't emit a structured event with the failed email, IP, and failure reason (invalid password vs. inactive account vs. unverified email). The middleware catches the 401 response, but can't distinguish between these failure modes. SOC 2 auditors specifically want to see categorized login failure reports.

W7: XSS Risk in Guest PDF Export

WARNING · SECURITY

app/services/guest_export_service.py · generate_guest_list_pdf()

Guest fields (names, phone, email, dietary info) are inserted directly into HTML templates without escaping before WeasyPrint renders them to PDF. A guest with a name containing <script> or malicious HTML could exploit this in the PDF rendering context. While WeasyPrint doesn't execute JavaScript, HTML injection could corrupt PDF layout or inject misleading content.

4. Informational Notes

I1: Middleware Stack Order Is Correct

INFO

app/main.py · lines 597–683

The middleware is registered outer-to-inner: ErrorHandler → SecurityHeaders → AuditLogging → Performance → RateLimit → CORS → GZip. The new ComplianceAuditMiddleware should register at position 3b (right after AuditLogging, slot #4) so it can capture the same request/response data. It should NOT replace AuditLogging — both run in parallel.

I2: TeamManagementService Already Uses ActivityLogService

INFO

app/services/team_management_service.py

This service already emits activity events for invite, accept, update, deactivate, reactivate, and remove actions. The compliance emitter should be additive — don't remove the existing activity log calls, as they feed the planner dashboard. Add compliance emission alongside them.

I3: Couple Portal Auth Uses Separate Cookie Path

INFO

app/api/couple_auth.py · app/dependencies/couple_auth.py

Couple authentication uses a separate cookie (couple_token) with its own token creation and verification. The compliance middleware needs to extract actor identity from both admin_token and couple_token cookies, not just the Bearer header. Also check for vendor portal token-based auth (/portal/[token]).

I4: Vendor Portal Uses Token-Based Access (No Cookie)

INFO

app/portal/[token]/ · app/contracts/[token]/

External vendors access the portal via URL tokens, not authenticated sessions. The compliance middleware must recognize these access patterns and log the actor as "vendor:{vendor_id}" with actor_type "vendor". The token itself should NOT be logged (security risk) — only the token-resolved identity.

5. Positive Observations

P1: Constant-Time Password Verification

GOOD

app/services/auth_service.py · line 30

Uses DUMMY_PASSWORD_HASH when user doesn't exist to prevent timing-based user enumeration. Well-implemented.

P2: Stripe Webhook Idempotency With Status Lifecycle

GOOD

app/services/stripe_service.py · lines 1400-1550

Full lifecycle tracking (processing → processed/failed) with DuplicateKeyError handling for race conditions. This is production-grade webhook handling.

P3: Existing Audit Middleware Is Non-Blocking

GOOD

app/middleware/audit_logging.py · line 236

Audit DB writes use asyncio.create_task() with a done callback for error surfacing. The new compliance emitter should follow this same pattern — never block the HTTP response for audit writes.

P4: Sensitive Data Sanitization Already Exists

GOOD

app/middleware/audit_logging.py · lines 142-163

The existing middleware already redacts passwords, tokens, API keys, credit cards, SSNs from logged data. The compliance emitter should reuse this sanitization logic.

P5: Cascade Delete Has Soft-Delete Option

GOOD

app/services/cascade_delete_service.py · line 64

The service supports both soft-delete (archive with deleted_at/deleted_by) and hard-delete. The compliance system should strongly prefer soft-delete and emit a pre-delete snapshot even for soft-delete operations.

P6: Existing Cloudflare Worker Patterns Are Reusable

GOOD

cloudflare-workers/autopilot-cron.js

The existing workers follow a consistent pattern: fetchWithTimeout(), CRON_SECRET auth, Resend email alerts on failure. The audit workers should follow the same conventions for consistency.
