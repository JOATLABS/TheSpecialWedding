# Messaging System Roadmap

## Objective
- Deliver a unified messaging workspace that supports planners, vendors, couples, and wedding party members across in-app chat and email.
- Maintain compliance with existing FastAPI role-based access controls while leveraging Firebase services for real-time synchronization and cost efficiency.
- Integrate messaging with core product workflows (forms, budgets, reminders) to keep communication context-rich and actionable.

## Requirements
### Functional
- Multi-party conversations with role awareness (`planner`, `vendor`, `couple`, `wedding_party`).
- Persistent message history with real-time updates for all active participants.
- Support for structured message attachments referencing forms, budgets, and reminders.
- Optional escalation to planner-owned Gmail accounts for sending and receiving email from within the messaging UI.
- Administrative dashboard views that surface unread counts, audit trails, and per-wedding conversation filters.

### Non-Functional
- Preserve existing Next.js + FastAPI deployment model; Firebase should be additive, not disruptive.
- Enforce strict access isolation between weddings and participant roles via Firebase Security Rules aligned with backend authorization policies.
- Capture audit logs for every message mutation, email send, or integration action.
- Leverage Firebase Spark/Blaze usage-based pricing to keep early-stage infrastructure costs minimal.
- Provide a clear rollback strategy and data export mechanism.

### Compliance & Security
- Use Firebase custom tokens generated by the FastAPI backend to ensure consistent identity across services.
- Store OAuth refresh tokens (for Gmail integration) encrypted in backend data stores with rotation policies.
- Respect GDPR-style data deletion requests by mirroring existing erasure workflows in Firestore and Gmail archives.
- Document subprocessors (Firebase, Google APIs) for vendor risk assessments and customer agreements.

## Configuration & Setup
### Backend-Centric Firebase Project Setup
1. Create a Firebase project and enable Cloud Firestore (native mode) and Cloud Functions before touching the frontend. This keeps the FastAPI integration path clear and lets the backend own lifecycle management from day one.
2. Generate service account keys for the Firebase Admin SDK and store them using the same secrets manager as the FastAPI database credentials. Capture the key rotation cadence in your runbooks.
3. Enable the Identity Toolkit API so custom token issuance from FastAPI is supported without friction.
4. Record the following environment variables for FastAPI (server side) and the Next.js client bundle separately:
   - Server: `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY`, `FIREBASE_DATABASE_URL` (if Realtime DB is enabled later).
   - Client: `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, `NEXT_PUBLIC_FIREBASE_APP_ID`, `NEXT_PUBLIC_FIREBASE_MEASUREMENT_ID` (optional).
5. Define IAM least-privilege roles: one service account for FastAPI write/read operations, another for automation tasks (Gmail sync, archival). Avoid reusing default service accounts to maintain audit clarity.

### Firestore Schema (initial)
- `conversations/{conversationId}`
  - Fields: `weddingId`, `createdAt`, `updatedAt`, `createdBy`, `channel` (`chat` or `email`), `subject`, `lastMessageSummary`, `metadata`
- `conversations/{conversationId}/participants/{participantId}`
  - Fields: `userId`, `role`, `joinedAt`, `mute`, `lastReadAt`
- `conversations/{conversationId}/messages/{messageId}`
  - Fields: `senderId`, `senderRole`, `body`, `attachments`, `linkedResource` (form/budget/reminder IDs), `deliveryStatus`, `emailMessageId`, `createdAt`
- Auxiliary collection: `conversationIndex` for fast planner dashboard queries (e.g., `plannerId`, `weddingId`, `lastActivityAt`, `unreadCount`).

### Firebase Security Rules (high level)
- Validate custom token claims for `userId`, `role`, and `weddingIds`.
- Allow read/write only if the participant exists in the `participants` subcollection and the role aligns with the requested operation.
- Restrict `channel: "email"` conversations to planners with Gmail integration enabled.

### Backend-Driven Gmail Integration
1. Register OAuth client credentials in Google Cloud Console with redirect URI pointing to `NEXT_PUBLIC_BASE_URL/api/integrations/google/callback`.
2. Implement OAuth flow in FastAPI (`/admin/integrations/gmail/auth` and `/admin/integrations/gmail/callback`) to obtain and store tokens.
3. Configure background sync (Cloud Function or FastAPI scheduled task) that:
   - Fetches Gmail history using stored tokens.
   - Upserts new messages into Firestore under the related conversation.
   - Updates `emailMessageId` and maintains label/metadata mapping.
4. Provide disconnect endpoint to revoke tokens and clean up Firestore metadata.

## Phased Delivery Plan (Backend-First)
### Phase 0 – Backend Foundations
- Finalize product requirements, participant roles, and data retention policies with emphasis on backend responsibilities.
- Stand up the Firebase project, enable APIs, and implement FastAPI-side configuration modules (`app/services/firebase/client.py`, `app/services/firebase/auth.py`) for Admin SDK access.
- Draft Firestore security rules in a dedicated repository directory and create accompanying FastAPI unit tests that exercise rule expectations through the Admin SDK emulator.
- Introduce continuous integration checks for the new backend modules (linting, type checking, emulator-backed tests) before touching the frontend.

### Phase 1 – Backend Messaging Services
- Implement Firestore conversation/message repositories inside FastAPI (e.g., `app/services/messaging/repository.py`) so all writes flow through validated backend logic.
- Expose REST endpoints for conversation CRUD, message send, and read receipts that operate on Firestore via the Admin SDK while enforcing existing dependency-injected permission guards.
- Add FastAPI endpoint to mint Firebase custom tokens post-authentication, returning them alongside existing JWT responses.
- Stand up background workers (Celery or async tasks) for message audit logging and archival exports, validating behavior in staging before frontend consumption.

### Phase 2 – Frontend Integration & Real-Time Hooks
- Scaffold shared configuration modules on the Next.js side (`app/lib/firebase/client.ts`, `app/hooks/messaging/useConversations.ts`, etc.) and connect them to the new backend token issuance flow.
- Build messaging UI components (Inbox layout, composer, unread indicators) leveraging Tailwind and existing design tokens, using Firestore listeners only after backend endpoints are validated.
- Launch an internal alpha for planners and vendors; collect feedback on UX/performance while monitoring backend telemetry.

### Phase 3 – Workflow Integrations
- Extend FastAPI messaging endpoints to accept structured attachments (forms, budgets, reminders) and coordinate with existing service modules before persisting Firestore metadata.
- Introduce Cloud Functions or backend tasks to synchronize message-triggered actions (e.g., send reminder emails via existing infrastructure) and confirm idempotency.
- Update planner dashboard summaries to include messaging metrics and quick filters, sourcing data through backend aggregations for consistency.
- Harden audit logging and export routines for compliance reviews, ensuring backend processes emit structured logs.

### Phase 4 – Gmail Connectivity
- Ship planner settings UI for Gmail OAuth connect/disconnect after backend token storage and revocation endpoints are production-ready.
- Implement background sync that maps Gmail threads to Firestore conversations using backend schedulers (or Cloud Functions) with robust retry policies.
- Enable sending email via the messaging composer, routing through FastAPI Gmail send endpoint with message logging and delivery status callbacks.
- Validate rate limits, retry logic, and user consent management before broad rollout; add automated regression tests for the Gmail services.

### Phase 5 – Optimization & Scale
- Monitor Firestore usage; tune indexes and data retention policies (archival, soft deletes) with backend cron jobs.
- Expand automated tests (unit/integration) covering Firestore hooks, backend token minting, and Gmail sync flows.
- Evaluate advanced features: AI-assisted replies, smart templates, analytics dashboards leveraging BigQuery exports, all mediated by backend orchestration.

## Integration with Existing Architecture
1. **FastAPI Backend (primary integration surface)**
   - Implement Firebase Admin SDK helpers and messaging repositories before exposing any new frontend features, keeping all Firestore writes within audited FastAPI routes.
   - Extend `app/main.py` with routers for token issuance, messaging CRUD, Gmail OAuth, and webhook-style callbacks while preserving dependency-injection patterns.
   - Reuse existing background task infrastructure for archival, sync, and compliance workflows triggered from Firestore changes.
   - Maintain parity between Firestore security rules and FastAPI permission guards (`require_wedding_planner`, `check_wedding_access`) to guarantee consistent authorization across services.

2. **Next.js Frontend (consumer of backend contracts)**
   - Initialize Firebase in client modules only after backend token issuance is live; authenticate via custom tokens acquired through `AdminContext` once the FastAPI login completes.
   - Reuse existing layout and routing to embed messaging views (`app/(dashboard)/messaging/page.tsx`, etc.), deferring to backend APIs for all mutations requiring validation.
   - Employ SWR/React Query patterns consistent with current data fetching, with Firestore listeners enhancing—not replacing—backend-sourced data when appropriate.

3. **Shared Services & Automations**
   - Trigger FastAPI workflows (forms, budgets, reminders) from messaging events via Cloud Functions or direct API calls that funnel into backend services first, ensuring a single source of truth for business logic.
   - Extend logging/monitoring stack to include Firestore operations, Gmail sync results, and messaging-related metrics for observability.

4. **Deployment Considerations**
   - Keep Next.js and FastAPI deployment pipelines unchanged (Docker/Vercel/Render); add Firebase configuration values to environment management.
   - Securely store Firebase service account keys and Gmail OAuth credentials using existing secrets management processes.
   - Plan backup/export routines (Firestore exports to Cloud Storage, Gmail message archiving) aligned with disaster recovery policies.
